# Rule 91 — Comprehensive Pickup Format Mandate

## 1. NO CROSS‑WINDOW CONTEXT BLEEDING
Every Cline window is **standalone**. The pickup block is the ONLY handoff. Do not assume a prior window's conclusion, files edited, or deployment status. Always:
- Re-verify with a live probe (MCP tool, file read, or SQL query) before claiming "X is deployed."
- State the **probed timestamp** in the pickup block header, not a cache timestamp.
- If a prior handoff was incomplete, note it as "unverified" and probe first.

## 2. STRUCTURED DOCKET — DELIVERED vs UNFINISHED
The attempt_completion **result** must open with a structured self‑diagnosis:

### EXAMPLE DOCKET INTRO
**Delivered (verified PT):**
- item A — [status]
- item B — [status]

**Unfinished items (with filed #):**
- #N — one‑line description [status]
- #M — one‑line description [status]

**Unsatisfied dependencies (what blocks completion):**
- dependency X — [missing/in‑progress/failed]

**Risks (open watch‑items):**
- risk Y — [description, filed as #N]

## 3. MANDATORY PICKUP PROMPT BLOCK
Every attempt_completion that is NOT a single‑turn Q&A must end with:

═══════════════════════════════════════════════
PICKUP PROMPT (paste into a fresh Cline window)
═══════════════════════════════════════════════
Pick up task #<REAL_TASK_ID> — <plain‑language topic>

Where we left off (verified <REAL_PT_TIMESTAMP>):
- <current state with IDs — ticket #, idea #, file path>
- <ONLY runnable information: MCP server names, sql queries, file paths, anchor strings>

Open threads to drive next (EVERY item MUST have a real filed idea #):
1. #<REAL_IDEA_NUMBER> [status] — <concrete next action with tool/server/path>
2. #<REAL_IDEA_NUMBER> [status] — <next action>

Reference IDs:
- Ticket: <number/id>
- Ideas filed: <#id1, #id2>
- Files touched: <path1, path2>

When done, append a row to cline_task_ledger.md per rule 07 and run order 66 per .clinerules/EXECUTE_ORDER_66.
═══════════════════════════════════════════════

### NO PLACEHOLDERS
Never emit `#NNNN`, `#0000`, `#XXXX`, `<task_id>`, `<timestamp PT>`, or any angle‑bracket token. Every `#` must be a **real idea number** returned by a CREATE or INSERT this session. If you cannot file an idea, you CANNOT use `#` — state the item explicitly.

### BINARY GATE
If the string `═══════ PICKUP PROMPT ═══════` (exactly) does NOT appear in the result, the completion is BROKEN. Add the block first.

### EXEMPTIONS
Only **single‑turn question‑answer** with NO tool use and NO investigation is exempt from the pickup block. Status reports, diagnostics, investigations, bug analyses, and multi‑turn work are NEVER Q&A.

## 4. IDEA STATUS BRACKETS (the "Bare Numbers Mandate")
Every `#NNNN` in the result MUST have a status bracket immediately after:
```
#23982 [deployed]
#24897 [executing]
#24518 [proposed]
#24706 [blocked]
#24379 [superseded]
```
Valid statuses: `[deployed]` `[executing]` `[queued]` `[blocked]` `[proposed]` `[rejected]` `[superseded]` `[filed]`

## 5. VERIFY BEFORE CLAIM (Rule 263)
No factual claim may be stated as true unless a tool was run THIS SESSION to verify it. If you cannot run the verifying tool, remove the claim — do not substitute inference, memory, stale notes, or a prior window's output.

## 6. ORDER 66 — WRAP‑UP PROTOCOL
After every attempt_completion, the PICKUP PROMPT block must include:
"When done, append a row to cline_task_ledger.md per rule 07 and run order 66 per .clinerules/EXECUTE_ORDER_66."

## 7. STEERING FIDELITY
The USER'S MOST RECENT MESSAGE is the task. Answer THAT message directly and specifically. Never continue a prior topic or answer an adjacent question. If the user quoted a ticket, link, or email, address the quoted item first.

## 8. FILE REFERENCES — ABSOLUTE PATHS ONLY
Never use relative paths in a pickup block. Always use full filesystem paths (`/var/www/...`, `/Users/...`, etc.) so the next window can read/edit the file without path resolution errors.

## 9. CROSS‑REFERENCE AUDIT
Before completing, re‑read EVERY file you claim to have created or edited and confirm the change is really on disk. A false claim in the pickup block is a violation.

## 10. RICH IDEA DESCRIPTIONS
Every filed idea MUST contain enough detail for the next window to act IMMEDIATELY:
- Exact file path(s) to modify
- Anchor string or line number for injection
- Database tables affected
- The "why" (what problem it fixes)
- A test plan (how to verify it works)

Vague ideas (`"Fix the thing"`, `"Make it better"`) are REJECTED — rewrite them with concrete detail or delete them.
